# Consumer migration and historical source epochs

The [dispositions](dispositions.json) assign every original143 consumer and the
additional indirect-reference/owner files to an explicit action, production
file, test owner and work item. The original surface inventory is preserved.
Whole-file hashes and exact reference-line hashes record the reviewed inputs.
The indirect scan includes ordinary certificate assembly, API routers and source
importers, certificate codecs, bundle selectors, build helpers and AI/release
tests missed by the original identity/symbol search. Owner dependencies are
listed separately from regex discoveries. This is a finite source-epoch audit;
T02 must extend it when a changed import or new consumer is discovered.

Private T02 migration is additive. Active selection and installed registries
stay unchanged until T07's complete image cutover. Retained frontends change
wire ownership, envelopes and hashes while retaining exact source capture,
admission, operations, contract demands and theorem meaning. Historical v1/v2
parsers and fixtures can remain isolated for compatibility verification. They
must not accept new semantics under an old schema. Inactive C# practical
identities and records stay reserved and unchanged; Go never activates that
profile as a prerequisite. Later C# work reconciles the Go-owned shared family.

Retained axiom policy uses the exact compiled context: Go zero axioms remains
zero; permitted Rust/C#/Java mvp-theory certificates retain their existing
formats, allowlists and five-category accounting. Observing two zero-axiom Rust
fixtures does not narrow that generic policy. Current private retained source
fixtures with an assembly error keep their original source and error result;
T07 must also exercise actual complete retained production workloads. Neither a
metadata model nor absence of a native Java AI run proves preservation.

The [requirement handoff](requirements.json) covers all24 v1 requirement groups,
their positive meaning, negative boundary, concrete design documents and
production/test owners. Design specification and later implementation/proof
verification have separate status. Every T02–T06 feature still needs meaningful
source-to-certificate examples, deliberately incorrect cases and both-checker
acceptance. T07/T11 still need complete native Linux release gates.

## Preserve old evidence without freezing future production

Historical `check_retained` helpers intentionally compare the exact production
and specification bytes from their own checkpoint. Editing those helpers or
replacing their observations to make a later source tree appear unchanged would
erase that evidence. Requiring all future code to keep the same bytes would
also prevent implementing the plan.

The [source epoch](historical-source-epoch.json) instead pins commit
`e19887077b7de9f512be72bfed52227ed4beebec`, tree
`27299259ca6fd04c63f23891fcdcdbe20e574333`. A real successful release checkpoint
reconstruction records its complete observed file-read closure plus its explicit
896 input pins and all historical Python package sources:1,025 tracked
files,218,743,291 bytes. Every SHA256 is checked against
the corresponding Git blob and executable mode. The
[replay](historical-replay.json) exports exactly those objects into a temporary
directory and runs the unchanged historical entry point there. It verifies the
same bytes/modes before and after execution, then removes the temporary tree.
No ref, checkout, installed file or historical helper is modified.

All Git calls, including read-only verification/export, use `/usr/bin/git`
outside the sandbox. The [epoch tool](../../../../probes/go-practical/source_epoch.py)
rejects a changed commit/tree, missing/replaced blob, unsafe or duplicate path,
wrong raw digest or executable mode. Replay is an historical reconstruction,
not a current-source build or new native run. Future W05/T02 evidence gets a
new source epoch and fresh execution; build caches/targets are separated by
epoch. A changed production byte invalidates current-source reuse while the
original historical checkpoint remains reproducible.

## Verification boundary

The audit checks design coverage, exact historical replay, distinct policy
allowances, statement/context-table binding and explicit resource values. It
does not simulate a materialized Go certificate. Existing169 Go requests remain
pending, both old Rust zero-axiom observations retain their original scope and
the four assembly-error fixtures remain intact. W05 owns inactive normative
publication and the cumulative T01 `check-fast` gate. That gate is deferred
through this W04 work, as required by the repository instructions.
